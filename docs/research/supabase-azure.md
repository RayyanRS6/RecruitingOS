FACTS:
1. PAGE IDENTITY: https://supabase.com/docs/guides/auth/social-login/auth-azure renders the title "Sign in with Azure (Microsoft)" (browser title "Sign in with Azure (Microsoft) | Supabase Docs"; meta description "Add Azure (Microsoft) OAuth to your Supabase project"). No "last updated" date is printed anywhere on the page; the only provenance link is "Edit this page on GitHub" pointing to apps/docs/content/guides/auth/social-login/auth-azure.mdx.

2. OVERVIEW (verbatim, auth-azure guide): "Setting up OAuth with Azure consists of four broad steps:" 1 "Create an OAuth application under Azure Entra ID." 2 "Add a secret to the application." 3 "Add the Supabase Auth callback URL to the allowlist in the OAuth application in Azure." 4 "Configure the client ID and secret of the OAuth application within the Supabase Auth dashboard."

3. ACCESS (verbatim, auth-azure guide, section "Access your Azure Developer account"): "Go to portal.azure.com." (link https://portal.azure.com/#home) and "Sign in and select Microsoft Entra ID under the list of Azure Services."

4. REGISTER (verbatim, auth-azure guide, section "Register an application"): "Under Microsoft Entra ID, select *App registrations* in the side panel and select *New registration.*" / "Choose a name and select your preferred option for the supported account types." / "Specify a *Web* *Redirect URI*. It should look like this: `https://<project-ref>.supabase.co/auth/v1/callback`" / "Finally, select *Register* at the bottom of the screen." The guide does NOT recommend a specific Supported account types option; it says "your preferred option".

5. REDIRECT URL FORMAT SUPABASE EXPECTS IN ENTRA (auth-azure guide): exactly `https://<project-ref>.supabase.co/auth/v1/callback`, registered under the *Web* platform. The page does not say where to find `<project-ref>`; the Management API sample on the same page uses the variable PROJECT_REF="your-project-ref" in the URL https://api.supabase.com/v1/projects/$PROJECT_REF/config/auth, i.e. the same project reference string that forms the project's supabase.co hostname.

6. LOCAL DEV NOTE (verbatim, auth-azure guide, callout "Local development with Azure OAuth"): "Azure does not allow `127.0.0.1` as a redirect URI hostname and requires the use of `localhost`." / "To enable Azure OAuth during local Supabase development, configure the Supabase API external URL in your `config.toml`:" code block: [api] external_url = "http://localhost:54321". Microsoft's reply-url page (ms.date 2025-05-14) corroborates: "You can't, however, use the **Redirect URIs** text box in the Azure portal to add a loopback-based redirect URI that uses the `http` scheme" and "**HTTP**: The HTTP scheme (`http://`) is supported *only* for *localhost* URIs".

7. CLIENT ID (verbatim, auth-azure guide, section "Obtain a client ID and secret"): "Once your app has been registered, the client ID can be found under the list of app registrations under the column titled *Application (client) ID*." / "You can also find it in the app overview screen." / "Place the Client ID in the Azure configuration screen in the Supabase Auth dashboard."

8. CLIENT SECRET (verbatim, auth-azure guide): "Select *Add a certificate or secret* in the app overview screen and open the *Client secrets* tab." / "Select *New client secret* to create a new client secret." / "Choose a preferred expiry time of the secret. Make sure you record this in your calendar days in advance so you have enough time to create a new one without suffering from any downtime." / "Once the secret is generated place the *Value* column (not *Secret ID*) in the Azure configuration screen in the Supabase Auth dashboard."

9. SUPABASE DASHBOARD FIELD LABELS: the auth-azure guide prints only ONE dashboard field label verbatim: "*Azure Tenant URL*" ("Configure this by storing a value under *Azure Tenant URL* in the Supabase Auth provider configuration page for Azure"). For the client ID and secret it only says "Place the Client ID in the Azure configuration screen" and "place the *Value* column ... in the Azure configuration screen in the Supabase Auth dashboard". The page does NOT print a dashboard menu path (no "Authentication", "Providers", or "Sign In / Providers" text), does NOT print an enable-toggle label, does NOT print the client-ID or secret input labels, and contains NO "skip nonce" text and NO "allow users without email" text.

10. MANAGEMENT API EQUIVALENT (verbatim from auth-azure guide, "You can also configure the Azure auth provider using the Management API:"): curl -X PATCH "https://api.supabase.com/v1/projects/$PROJECT_REF/config/auth" with JSON body keys "external_azure_enabled": true, "external_azure_client_id": "your-azure-client-id", "external_azure_secret": "your-azure-client-secret", "external_azure_url": "your-azure-url". The Management API reference (https://supabase.com/docs/reference/api/v1-update-auth-service-config) lists exactly five azure properties, all with no description: external_azure_enabled (boolean), external_azure_client_id (string), external_azure_email_optional (boolean), external_azure_secret (string), external_azure_url (string). The only nonce property on that reference is external_google_skip_nonce_check; there is no external_azure_skip_nonce_check.

11. TENANT URL SECTION (verbatim, auth-azure guide, heading "Configure a tenant URL (optional)"): "A Microsoft Entra tenant is the directory of users who are allowed to access your project. This section depends on what your OAuth registration uses for *Supported account types.*" / "By default, Supabase Auth uses the *common* Microsoft tenant (`https://login.microsoftonline.com/common`) which generally allows any Microsoft account to sign in to your project. Microsoft Entra further limits what accounts can access your project depending on the type of OAuth application you registered."

12. TENANT URL VALUES (verbatim, auth-azure guide): "If your app is registered as *Personal Microsoft accounts only* for the *Supported account types* set Microsoft tenant to *consumers* (`https://login.microsoftonline.com/consumers`)." / "If your app is registered as *My organization only* for the *Supported account types* you may want to configure Supabase Auth with the organization's tenant URL. This will use the tenant's authorization flows instead, and will limit access at the Supabase Auth level to Microsoft accounts arising from only the specified tenant." / "Configure this by storing a value under *Azure Tenant URL* in the Supabase Auth provider configuration page for Azure that has the following format `https://login.microsoftonline.com/<tenant-id>`." So: multi-tenant / any-account registration = leave Azure Tenant URL empty (defaults to common); single-tenant = https://login.microsoftonline.com/<tenant-id>; personal-only = https://login.microsoftonline.com/consumers. The guide never mentions an `organizations` endpoint.

13. PERSONAL MICROSOFT ACCOUNTS: supported. The guide explicitly covers the "Personal Microsoft accounts only" registration (tenant `consumers`) and says the default common tenant "generally allows any Microsoft account to sign in to your project".

14. EMAIL SCOPE (verbatim Note on auth-azure guide, section "Add sign-in code to your client app"): "Supabase Auth requires that Azure returns a valid email address. Therefore you must request the `email` scope in the `signInWithOAuth` method." JavaScript sample: supabase.auth.signInWithOAuth({ provider: 'azure', options: { scopes: 'email' } }). Kotlin: scopes.add("email"). C#: "Request the `email` scope:" SignInOptions { Scopes = "email" }. The Flutter sample on the page passes only redirectTo and authScreenLaunchMode (no scopes shown).

15. DEFAULT SCOPES: the auth-azure guide does NOT list which scopes Supabase requests by default. It only states that `email` must be requested and that `offline_access` is needed for a provider refresh token.

16. PROVIDER REFRESH TOKEN (verbatim, auth-azure guide, heading "Obtain the provider refresh token"): "Azure OAuth2.0 doesn't return the `provider_refresh_token` by default. If you need the `provider_refresh_token` returned, you will need to include the following scope:" JS sample scopes: 'offline_access' (Flutter scopes: 'offline_access', Kotlin scopes.add("offline_access"), C# Scopes = "offline_access"). Related overview page https://supabase.com/docs/guides/auth/social-login states Supabase Auth does not refresh provider tokens for you and does not store provider tokens in the project database.

17. UNVERIFIED EMAIL CAVEAT (verbatim, auth-azure guide, heading "Guarding against unverified email domains"): "Microsoft Entra ID can send out unverified email domains in certain cases. This may open up your project to a vulnerability where a malicious user can impersonate already existing accounts on your project." / "This only applies in at least one of these cases:" bullets: "You have configured the `authenticationBehaviors` setting of your OAuth application to allow unverified email domains" / "You are using an OAuth app configured as single-tenant in the supported account types" / "Your OAuth app was created before June 20th 2023 after Microsoft announced this vulnerability, and the app had used unverified emails prior" / "This means that most OAuth apps *are not susceptible* to this vulnerability."

18. XMS_EDOV STEPS (verbatim, auth-azure guide): "Despite this, we recommend configuring the optional `xms_edov` claim on the OAuth app. This claim allows Supabase Auth to identify with certainty whether the email address sent over by Microsoft Entra ID is verified or not." / "Configure this in the following way:" 1 "Select the *App registrations* menu in Microsoft Entra ID on the Azure portal." 2 "Select the OAuth app." 3 "Select the *Manifest* menu in the sidebar." 4 "Make a backup of the JSON in case you need it later." 5 "Identify the `optionalClaims` key." 6 "Edit it by specifying the following object:" (JSON, 25 lines: "optionalClaims": { "idToken": [ {"name": "xms_edov", "source": null, "essential": false, "additionalProperties": []}, {"name": "email", "source": null, "essential": false, "additionalProperties": []} ], "accessToken": [ {"name": "xms_edov", "source": null, "essential": false, "additionalProperties": []}, ... ] }) 7 "Select *Save* to apply the new configuration."

19. XMS_EDOV DEFINITION (Microsoft, https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference, ms.date 2026-07-22, updated_at 2026-08-20, verbatim row): `xms_edov` "Boolean value indicating whether the user's email domain owner has been verified." Token Type JWT. Notes: "An email is considered to be domain verified if it belongs to the tenant where the user account resides and the tenant admin has done verification of the domain. Also, the email must be from a Microsoft account (MSA), a Google account, or used for authentication using the one-time passcode (OTP) flow. Facebook and SAML/WS-Fed accounts **do not** have verified domains. For this claim to be returned in the token, the presence of the `email` claim is required." Same page, `email` row: "This value is included by default if the user is a guest in the tenant. For managed users (the users inside the tenant), it must be requested through this optional claim or, on v2.0 only, with the OpenID scope."

20. PKCE NOTES (verbatim, auth-azure guide): "For a PKCE flow, for example in Server-Side Auth, you need an extra step to handle the code exchange. When calling `signInWithOAuth`, provide a `redirectTo` URL which points to a callback route. This redirect URL should be added to your redirect allow list." (links /docs/guides/auth/redirect-urls) / "At the callback endpoint, handle the code exchange to save the user session." Tab "Client": "In the browser, `signInWithOAuth` automatically redirects to the OAuth provider's authentication endpoint, which then redirects to your endpoint." Tab "Server": "In the server, you need to handle the redirect to the OAuth provider's authentication endpoint. The `signInWithOAuth` method returns the endpoint URL, which you can redirect to." Caution: "Use a server client from `@supabase/ssr`, and send its cookies with the redirect. `signInWithOAuth` stores the PKCE code verifier in a cookie. When that `Set-Cookie` header doesn't reach the browser, the callback can't exchange the code for a session." Callback samples (Next.js app/auth/callback/route.ts, SvelteKit, Astro, Remix, Express) all call supabase.auth.exchangeCodeForSession(code) and on failure redirect to /auth/auth-code-error.

21. PKCE FLOW PAGE (https://supabase.com/docs/guides/auth/sessions/pkce-flow, no last-updated date printed, verbatim): "The Proof Key for Code Exchange (PKCE) flow is one of two ways that a user can authenticate and your app can receive the necessary access and refresh tokens." / "For security purposes, the code has a validity of 5 minutes and can only be exchanged for an access token once." / "The code verifier is created and stored locally when the Auth flow is first initiated. UNCERTAINTIES:
1. The Supabase Azure guide does not print the dashboard provider screen's labels except "Azure Tenant URL"; the exact labels for the enable toggle, client ID input, secret input, any email-optional toggle, and the menu path to reach the Azure provider are not on any page I could read without logging in to the Supabase dashboard (not attempted). The Management API property external_azure_email_optional exists but has no description on the reference page, so its dashboard wording and behaviour are unverified.

2. No Supabase docs page I read prints a "last updated" date; freshness is only inferable from the GitHub source link. Microsoft pages expose ms.date/updated_at metadata (quoted per page) rather than a visible date.

3. The guide never lists Supabase's default OAuth scopes for Azure; it only says `email` must be requested and `offline_access` is needed for provider_refresh_token.

4. Entra UI wording is inconsistent across sources: the Supabase guide uses "Personal Microsoft accounts only" and "My organization only"; Microsoft's current quickstart (ms.date 2026-05-14) uses drop-down options "Single tenant only - <your tenant>", "Multiple Entra ID tenants", "Any Entra ID Tenant + Personal Microsoft accounts", "Personal accounts only"; Microsoft's reply-url page (ms.date 2025-05-14) still uses the older "Accounts in this organizational directory only (... - Single tenant)" style. Which wording the live Entra admin center shows on 22 Sep 2026 must be confirmed on screen.

5. The Supabase guide says to "Specify a *Web* *Redirect URI*" on the registration form, but Microsoft's current quickstart has no redirect URI step at registration and Microsoft's how-to places it under Manage > Authentication > "Redirect URI configuration" tab > "Add Redirect URI". Either path may appear depending on portal version; the callback URL value is the same.

6. The Microsoft page the Supabase guide links for xms_edov (learn.microsoft.com/en-us/azure/active-directory/develop/migrate-off-email-claim-authorization#...) now returns the generic "Microsoft identity platform documentation" hub page (HTTP 200, no xms_edov content, no redirect header); the guide's linked anchor content appears retired. The xms_edov definition was taken from Microsoft's optional-claims-reference page instead. The Supabase guide's "authenticationBehaviors" and "June 20th 2023" statements could therefore not be re-verified against the originally linked Microsoft page.

7. In the guide's 25-line optionalClaims JSON, my extraction confirmed xms_edov and email under idToken and xms_edov under accessToken; the final entries under accessToken were truncated in my capture, so copy that block from the live page rather than from this report.

8. Microsoft's credentials page says client secrets should not be used in production and recommends certificates, whereas the Supabase Azure guide and Management API only accept a client secret; no certificate-based option is documented on the Supabase side.

9. The Supabase guide's statement that Azure requires `localhost` rather than `127.0.0.1` is consistent with Microsoft's reply-url page only for the http scheme (Microsoft says http loopback 127.0.0.1 cannot be added via the portal text box but https://127.0.0.1 is valid); the Supabase wording is broader than Microsoft's.

10. All Supabase page text was decoded from the page's Next.js server payload (WebFetch's summarizer had condensed it); label quoting is from that payload and the raw HTML, not from a rendered screenshot.
