4. API KEY MODEL — four key types (API keys page, 'Key types' table, verbatim): "Publishable key | sb_publishable_... | Low | Platform, CLI | Safe to expose online: web page, mobile or desktop app, GitHub actions, CLIs, source code." — "Secret keys | sb_secret_... | Elevated | Platform, CLI | Only use in backend components of your app, such as servers, APIs with their own authorization checks, Edge Functions, and microservices. They provide full access to your project's data, bypassing Row Level Security." — "anon | JWT (long-lived) | Low | Platform, CLI | Legacy version of publishable keys." — "service_role | JWT (long-lived) | Elevated | Platform, CLI | Legacy version of secret keys." Also: "Publishable and secret keys are short strings, not JWTs. If a tool, tutorial, or AI assistant tells you to copy a long key that begins with eyJ, it was written for the legacy keys."

5. API KEYS — dashboard location (API keys page, exact wording): "To pick a specific key, or to see every key your project has, open the Settings > API Keys section of the Dashboard instead. Every key lives there, legacy or not, and there is no separate Settings > API page." Dashboard link printed on the page: https://supabase.com/dashboard/project/_/settings/api-keys/. The migration page (https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) names the tab "Publishable and secret API keys" under "Settings > API Keys", and says "Older projects don't have these keys yet. If you see a Create new API keys button, your project is still on legacy keys only."

6. API KEYS — both systems coexist (API keys page, 'Legacy anon and service_role keys' section, verbatim): "Creating publishable and secret keys doesn't revoke your legacy keys. Both key systems work at the same time." and "Creating a publishable or secret key adds it alongside your existing anon and service_role keys without affecting them, so your legacy keys keep working. They stay valid until you disable them in the Settings > API Keys section of the Dashboard, which is a separate step." Whether a brand-new project is created with BOTH legacy and new keys is NOT stated on either page (see uncertainties).

7. API KEYS — deprecation timeline (API keys page and migration page, identical sentence): "Supabase is deprecating the anon and service_role keys by the end of 2026. Use the publishable (sb_publishable_xxx) and secret (sb_secret_xxx) keys instead. For the reasoning behind the change, see the announcement on GitHub." No other date is given; no deprecation date is given anywhere for the legacy JWT secret itself.

8. API KEYS — apikey header rule (API keys page, 'Known limitations', verbatim): "Send publishable and secret keys on the apikey header, not on Authorization: Bearer. Because the keys aren't JWTs, anything that tries to verify one as a JWT fails. For migration compatibility the verify_jwt platform check accepts them on either header, but passing that check doesn't authenticate the caller." The migration page adds: "User authentication through Supabase Auth is unchanged. The user still signs in and gets their own JWT." and "The platform's built-in verify_jwt check only understands the legacy JWT-based keys, so set verify_jwt = false for these functions and authorize the request in your own code." The self-hosting page (https://supabase.com/docs/guides/self-hosting/self-hosted-auth-keys) lists the header as "apikey - the API key (sb_ or legacy JWT)". NO page explicitly names /auth/v1/token?grant_type=pkce or /auth/v1/authorize as accepting a publishable key (see uncertainties).

9. API KEYS — role mapping (API keys page table): "Publishable key | No [user signed in] | anon", "Publishable key | Yes | authenticated", "Secret key | Not applicable | service_role". Secret-key browser block: "A secret key doesn't work in a browser. Supabase matches on the User-Agent header and returns HTTP 401 Unauthorized." Local CLI: "Running supabase start prints a publishable key and a secret key for your local project. The local secret key takes the place of the local service_role key." Edge Functions runtime: "SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY still exist in the runtime, but they carry the legacy keys, so reading them keeps you on the deprecated path."

10. SECRET HANDLING RULES (API keys page, 'Handling secret keys safely', verbatim): "How a secret key must never travel: Over chat, email, or SMS. In a URL or a query parameter, because those are often logged. In a request header, until you have log sanitization in place." and "Share keys through an encrypted transfer tool, such as the one in your password manager. Better still, have the other person read the key from the Settings > API Keys section of the Dashboard." This supports the user's rule: only the Reference ID, project URL and publishable key are non-secret; sb_secret_..., service_role, the legacy JWT secret and any DB password are secrets to be entered directly at their destination.

11. JWT SIGNING KEYS — dashboard location. Signing keys page (https://supabase.com/docs/guides/auth/signing-keys) links the "JWT signing keys page" to https://supabase.com/dashboard/project/_/settings/jwt. Troubleshooting page 'Rotating Anon, Service, and JWT Secrets' (https://supabase.com/docs/guides/troubleshooting/rotating-anon-service-and-jwt-secrets-1Jq6yd) prints the path as "Go to Project Settings → JWT Keys in the Supabase Dashboard" then "Navigate to the JWT Signing Keys tab." then "Click on Rotate Keys. This will move the current key to 'Previously used keys'" then "Select the three-dot icon (action icon) of your previously used key and click 'Revoke'. If you do not 'Revoke' the key, older keys will still be valid." That page also states: "We recommend that you migrate to asymmetric JWT signing keys and publishable/secret API keys as it is no longer possible to rotate the legacy anon, service and JWT secrets." A tab literally named 'Legacy JWT Secret' is NOT named on any page I read.

12. JWT SIGNING KEYS — legacy vs asymmetric model (signing keys page, verbatim): "Legacy | JWT secret | Initially Supabase was designed to use a single shared secret key to sign all JWTs. This includes the anon and service_role keys, all user access tokens including some Storage pre-signed URLs. No longer recommended. Available for backward compatibility." Algorithm table: "RSA 2048 (Asymmetric) RS256 ... We recommend using the P-256 elliptic curve instead."; "Ed25519 Curve (Asymmetric) EdDSA Coming soon."; "HMAC with shared secret (Symmetric) HS256 Not recommended for production applications." (ES256 / NIST P-256 is the recommended asymmetric option; CLI example: supabase gen signing-key --algorithm ES256). JWKS endpoint printed verbatim: "GET https://project-id.supabase.co/auth/v1/.well-known/jwks.json"; caching: "This discovery endpoint is cached by Supabase's edge servers for 10 minutes. Furthermore the Supabase client libraries may cache the keys in memory for an additional 10 minutes." and "Supabase products (Auth, Data API, Storage, Realtime) do not rely on this cache and revocation is instantaneous." JWTs page adds: "Be aware that this endpoint does not return any keys if you are not using asymmetric JWT signing keys."

13. JWT SIGNING KEYS — migration steps and exact button labels (signing keys page, 'Getting started', verbatim): "Start off by clicking the Migrate JWT secret button on the JWT signing keys page. This step will import the existing legacy JWT secret into the new JWT signing keys system." — "Simultaneously, we're creating a new asymmetric JWT signing key for you to rotate to. This key starts off as standby key" — "If you do wish to start using the standby key for all new JWT use the Rotate keys button." — warnings: "Make sure your app does not directly rely on the legacy JWT secret." and "If you're using Edge Functions that have the Verify JWT setting, continuing with the rotation might break your app. You will need to turn off this setting." — "Rotating the keys immediately causes the Auth server to issue new JWT access tokens for signed in users signed with the new key. Non-expired access tokens will remain to be accepted, so no users will be forcefully signed out." — "If your access token expiry time is configured to be 1 hour, wait at least 1 hour and 15 minutes before revoking the legacy JWT secret -- now under the Previously used section." Key states named on the page: standby, in use (current key), previously used, revoked; actions table: "Create a new key", "Rotate keys", "Revoke key", "Move to standby from revoked", "Move to standby from previously used", "Delete key". FAQ: "Why is deleting the legacy JWT secret disallowed? This is to ensure you have the ability, should you need it, to go back to the legacy JWT secret." and "before you revoke the legacy JWT secret, you must disable the anon and service_role to ensure a consistent security setup."

18. REDIRECT URL WILDCARD RULES (Redirect URLs page, table verbatim): "* — matches any sequence of non-separator characters"; "** — matches any sequence of characters"; "? — matches any single non-separator character"; "c — matches character c (c != *, **, ?, \\, [, {, })"; "\\c — matches character c"; "[!{ character-range }] — matches any sequence of characters not in the { character-range }. For example, [!a-z] will not match any characters ranging from a-z." — "The separator characters in a URL are defined as . and /." Examples: "http://localhost:3000/* matches http://localhost:3000/foo, http://localhost:3000/bar but not http://localhost:3000/foo/bar or http://localhost:3000/foo/ (note the trailing slash)"; "http://localhost:3000/** matches http://localhost:3000/foo, http://localhost:3000/bar and http://localhost:3000/foo/bar"; "http://localhost:3000/? matches http://localhost:3000/a but not http://localhost:3000/foo"; "http://localhost:3000/[!a-z] matches http://localhost:3000/1 but not http://localhost:3000/a". Recommendation box: "While the 'globstar' (**) is useful for local development and preview URLs, we recommend setting the exact redirect URL path for your site URL in production."

UNCERTAINTIES:
1. Whether a newly created hosted project (such as recruiting-os-staging) is provisioned with BOTH the legacy anon/service_role JWT keys AND the new publishable/secret keys is not stated verbatim on the API keys or migration pages. The migration page only says "Older projects don't have these keys yet. If you see a Create new API keys button, your project is still on legacy keys only." — so the practical check is: open Settings > API Keys and see whether a 'Create new API keys' button appears (legacy-only) or a 'Publishable and secret API keys' tab already lists sb_publishable_/sb_secret_ keys.

2. No official docs page explicitly states that a publishable key is accepted as the apikey header on the Auth endpoints /auth/v1/token?grant_type=pkce or /auth/v1/authorize. The docs say generically "Send publishable and secret keys on the apikey header", that "User authentication through Supabase Auth is unchanged", and (self-hosting page) "apikey - the API key (sb_ or legacy JWT)". Treat use of sb_publishable_ on Auth REST endpoints as documented-by-implication only; verify with a test call against the staging project.

3. What NEW projects use by default for JWT signing (legacy shared HS256 secret vs an asymmetric ES256 key) is not stated on the signing-keys, jwts, or self-hosting docs pages. A web search snippet attributed 'New projects use asymmetric signing keys by default' to a non-docs Supabase marketing/blog page, which is outside the allowed sources, so it is unverified. Practical check: open Project Settings > JWT Keys on the staging project and look for a 'Migrate JWT secret' button (present = still on legacy secret) or an existing ES256 current key; also GET https://<ref>.supabase.co/auth/v1/.well-known/jwks.json — the JWTs page says it "does not return any keys if you are not using asymmetric JWT signing keys".

4. The exact dashboard field/tab label under which the legacy JWT secret is displayed (e.g. a 'Legacy JWT Secret' tab) is not printed on any page read; the docs only give the page path (Project Settings → JWT Keys, https://supabase.com/dashboard/project/_/settings/jwt) and say "You can only extract the legacy JWT secret."

5. The literal field label 'Project URL' and the exact sidebar labels 'Authentication > URL Configuration' and 'Authentication > Multi-Factor' are not printed on the docs pages; the docs give only the link texts 'URL Configuration' and 'Authentication Settings' with dashboard paths /auth/url-configuration and /auth/mfa, and the Connect dialog for the URL. Dashboard wording may differ slightly from what the docs print.

6. The troubleshooting page on rotating secrets contains a visible typo ("Project Settings → JWT Keyss"); I reported it as 'JWT Keys'. Troubleshooting pages are community-style articles and may lag behind dashboard changes.

7. The pricing page rows were confirmed by label ('Basic Multi-Factor Auth', 'Advanced Multi-Factor Auth - Phone') in the raw HTML, but the per-plan cell values ('Included', 'Not included', '$75 per month...', 'Custom') came from the fetch tool's rendering of the table rather than a raw grep, so the column-to-plan mapping should be eyeballed once on supabase.com/pricing before being quoted to the founder.
