# 04. Data model and event taxonomy

Postgres 16+, pgvector. Every tenant table carries `company_id` and is protected by row-level security. Primary keys are UUIDv7 (time-ordered) except the append-only `events` and `jobs` tables, which use bigserial. Timestamps are `timestamptz`. JSON columns hold objects validated by Zod schemas in `packages/contracts`; the schema name is noted in brackets.

## Relationships (the ones that matter)

```
companies 1─* memberships *─1 users
companies 1─* roles 1─* role_packets (versions)
companies 1─* invitations
roles 1─* postings ; roles 1─* application_links (a board's own link carries posting_id) ; application_links 1─* applications (link_id)
roles 1─* applications *─1 candidates
applications 1─* assessments, screens, interviews, scorecards, communications, offers
applications 1─1 onboardings 1─* hiring_outcomes
interviews 1─* interview_participants, scorecards
applications 1─* interview_followups (at most one open) *─1 interviews
roles 1─* debriefs
companies 1─* policies (role_id null = default) ; roles 1─* policies (overrides)
workflow_runs 1─* workflow_steps ; workflow_runs 1─* ai_runs ; workflow_runs 1─* approval_requests
recruiter_escalations *─1 roles/applications ; takeovers *─1 roles
events: everything, by subject and correlation
```

## Indexes

- Every tenant table: `(company_id)` plus the natural access path, e.g. `applications (company_id, role_id, stage)`, `applications (company_id, candidate_id)`, `candidates (company_id, dedupe_key)` unique partial, `candidates (company_id, email)`, `communications (company_id, candidate_id, created_at desc)`, `events (company_id, occurred_at desc)`, `events (subject_type, subject_id, occurred_at)`, `events (type, occurred_at)`, `workflow_runs (status, updated_at)`, `jobs (status, run_at)` for the poller, `ai_runs (company_id, created_at desc)`, `ai_runs (task, created_at desc)`, `approval_requests (company_id, status)`, `recruiter_escalations (status, created_at)`.
- Full text: `documents.text_extracted` (tsvector generated column) for recruiter search.
- Vector: `candidates.embedding` HNSW (cosine) for rediscovery, created when the table exceeds a few thousand rows; sequential scan is fine before that.

## Tenant boundary and permissions

- RLS policy on every tenant table: `USING (company_id = current_setting('app.company_id', true)::uuid)`. The API sets `app.company_id` per transaction from the session's active membership. Platform admins connect with `app.bypass_rls = on` under a separate database role, and every such query path writes an `audit_records` row.
- Object-level permissions live in `packages/core/src/permissions.ts`: a matrix of role × action × object with predicates (an interviewer may read an application only if they are a participant in one of its interviews; nobody except owner/admin/hr/recruiter reads compensation; candidates access only their own application through signed tokens).
- PGlite runs RLS the same way, so tests assert cross-tenant reads return nothing.

## Lifecycle states

Role: `draft → pending_approval → open ⇄ paused → filled | closed` (a rejected or expired approval returns `pending_approval` to `draft`; the accepting switch is separate from the status). Posting: the nine states of `POSTING_TRANSITIONS` in `packages/core/src/postings.ts`; `closed` is terminal and a re-opened role prepares its rows again. Invitation: `pending → accepted | revoked`, or expired by date. Role packet: `proposed → approved → superseded`. Application: doc 06. Offer: `draft → pending_approval → approved → sent → viewed → (negotiating →)* accepted | declined | expired | rescinded`. Workflow run: `running ⇄ waiting → completed | failed | cancelled | paused`. Escalation: `open → claimed → in_progress → resolved | cancelled`.

## Event taxonomy

Naming: `subject.past_tense_verb`. Every event has `actor`, `subject`, `correlation_id`, and a typed payload (`packages/contracts/src/events.ts`).

**Company and users:** `company.created`, `company.updated`, `user.invited`, `user.joined`, `membership.changed`, `member.joined` (an invitation accepted at sign-in), `member.removed`, `invitation.revoked`, `integration.connected`, `integration.failed`, `policy.changed`, `plan.changed`, `entitlement.exceeded`. Invitations are rows of their own (`invitations`, migration 0022): company, lower-cased address, role, who sent it, the token's hash, status pending / accepted / revoked (expired is read from the seven-day `expires_at`). `company.updated` carries the changed keys of a `PATCH /companies/current`.

**Intake and role:** `intake.started`, `intake.turn_completed`, `intake.compiled`, `role.created`, `role_packet.proposed`, `role_packet.approved`, `role_packet.edited`, `role.approved`, `role.opened`, `role.paused`, `role.resumed`, `role.filled`, `role.closed` (carries `closureRequired`: the board channels still up), `role.sent_back` (a packet approval was rejected or expired after 14 days; the role is a draft again), `role.applications_closed`, `role.applications_reopened` (the accepting switch), `role.volume_high` (`{day, count, threshold}`, once a day per role in the company's time zone).

**Packet tools (the job builder, plan Wave C):** `packet.revision_proposed` (the assistant proposed a change by chat; nothing saved; `{revisionId, sections, notChanged, asked, newFlags}`, plus `{roleId, baseVersion}` on a role), `packet.revision_applied` (a person confirmed it: a new version with source `agent_revision`, or the draft rewritten before the role exists), `packet.revision_discarded` (a person set it aside; the proposal can no longer be saved), `packet.check_applied` (a person applied fixes from the requirements check; `{applied, skipped}`). The proposal itself is the `ai_runs` row of the `packet.revise` run; its `final_outcome` records whether it was applied (and as which version) or set aside.

**Posting (docs/spec/20):** one event per state a posting enters, emitted by `transitionPosting` with `{channel, roleId, from, to, url, reason}`: `posting.draft`, `posting.approved`, `posting.ready_to_post`, `posting.posted_manually`, `posting.submitted_integration`, `posting.live_verified`, `posting.paused`, `posting.failed`, `posting.closed`; plus `posting.verification_failed` (`{reason, detail, attempt, final}`), `posting.closure_required`, `posting.closure_confirmed`, `application_link.created` and `application_link.disabled` (never the token). `posting.requested`, `posting.expired` and `posting.spend_recorded` remain in the enum; the old `posting.published`, `posting.awaiting_verification`, `posting.manual_action_required` and `posting.not_connected` stay only so stored history still validates, and nothing emits them.

**Application:** `application.received`, `application.acknowledged`, `application.duplicate_detected`, `candidate.created`, `candidate.merged`, `resume.ingested`, `resume.extraction_failed`, `eligibility.evaluated`, `application.ineligible`, `application.triaged`, `assessment.created`, `application.stage_changed`, `application.inactive`, `application.withdrawn`, `application.rejected`, `application.moved_to_talent_pool`. `application.received` carries `source` and `linkId`, never the link's token. `pool.batch_applied` (subject: the role) records one Review and apply on the pool board (plan F8): `{batchId, suggestedBy: "assistant", appliedBy, items: [{applicationId, suggested, chosen, ok, code}], applied, refused, followedSuggestion}`; each decision it made also carries `via: "review_and_apply"`, `batchId`, `suggested` on its own `application.rejected`, `application.stage_changed` and `human.override` events, and a mark it set has `source: "board"`.

**Team notes (plan H3, founder decision Q24):** `note.added` and `note.updated` (subject: the application) say that a team member wrote, changed (`version`) or removed (`removed: true`) their private note, with `noteId`, `starter` and `authorRole`; never the words. The words live in `application_notes` (one live note per person per application, earlier versions in `previous_versions`, removed notes kept with `deleted_at`; migration 0034). **Offer made (plan H2, Q29):** `offer.created` (subject: the application; `madeOutside: true`, `madeOn`), then `offer.accepted`, `offer.declined` or `offer.rescinded` when the answer is recorded; the `offers` row has `made_outside`, `made_on` and empty terms.

**Screening:** `screen.invited`, `screen.started`, `screen.completed`, `screen.abandoned`, `screen.expired`, `screen.human_requested`, `screen.assessed`.
